# Задачи

Проект: `/opt/zerocams-react` — React 18.3.1 + Vite 5.4 (JS/JSX, НЕ TypeScript), react-router-dom 6.26.2.

## Задача 1. Вынести вендоров в отдельные чанки (`manualChunks`)

**Проблема.** В сборке чанк ленивой страницы `PTZControl-*.js` весит 627.60 kB (gzip 197.12 kB). Причина — в него попадает `hls.js` (~500 kB сырого кода), потому что `HLSPlayer.jsx` (импортирует `hls.js`) и `PTZControl.jsx` оказываются в одном ленивом чанке по эвристике Vite. Из-за этого библиотека перекачивается при каждом деплое, хотя не менялась.

**Что сделать.** В `vite.config.js` (сейчас там только `plugins` и `server.port`, без `build`) добавить `build.rollupOptions.output.manualChunks`, разложив хотя бы:
- `react`, `react-dom`, `react-router-dom` → отдельный vendor-чанк;
- `hls.js` → отдельный vendor-чанк.

**Проверка.** `npm run build` — `PTZControl` чанк должен упасть до размеров собственно компонента; `hls.js` — отдельный файл, который кэшируется браузером независимо от деплоя.

**Ожидаемый эффект.** Суммарный вес первого захода не меняется, но повторные заходы и апдейты дешевеют.

## Задача 2. Ленивая загрузка тяжёлых страниц

**Проблема.** `index-*.js` в сборке ~277 kB — это React + роутер + все страницы, которые заимпорчены статически. Нужно найти статические импорты страниц (особенно админка, редакторы, плееры) и перевести их на `React.lazy` + `Suspense`, чтобы index-чанк уменьшился.

**Что сделать.** Найти файл с роутингом (скорее всего `src/App.jsx`), проверить, какие страницы импортированы статически, и перевести тяжёлые на `lazy(() => import(...))`. Обязательно нужен `<Suspense fallback={...}>` вокруг маршрутов.

**Важно.** Не ломать поведение: страницы должны открываться так же, как сейчас. Проверить, что каждая ленивая страница имеет корректный fallback и не роняет приложение при быстром переключении.

**Проверка.** `npm run build` — index-чанк должен уменьшиться, появиться отдельные чанки страниц.

## Задача 3. Проверка доступности WebRTC каждые несколько секунд + ленивая загрузка hls.js

Пользователь явно попросил: **проверка доступности WebRTC должна идти не один раз, а периодически** (каждые несколько секунд), и hls.js должен грузиться по требованию (только когда реально нужен HLS).

### 3a. Периодическая проверка WebRTC

**Где.** Файл проверки: `src/api/webrtcCheck.js`. Сейчас `checkWebRTCAvailability()` кэширует результат навсегда в модульной переменной `webrtcAvailable` и делает один `fetch` к `${WS_BASE_URL→http}/config?v=<VITE_APP_VERSION>`; результат — `response.status === 200`. Есть также `resetWebRTCCheck()`.

**Что сделать.** Сделать так, чтобы проверка повторялась время от времени (интервал порядка нескольких секунд — подобрать разумное значение, например 5–10 с), а не выполнялась однократно. Учесть:
- не спамить сервер: не запускать параллельные проверки (в файле уже есть защита через `checkPromise` — сохранить её);
- не накапливать таймеры/подписки: при размонтировании компонента-потребителя очищать интервал;
- не дёргать проверку чаще, чем нужно, когда вкладка неактивна (`document.visibilityState`) — по возможности.

**Кто потребитель.** `src/components/cams/VideoStreamUniversal.jsx` — вызывает `checkWebRTCAvailability()` в `useEffect` загрузки форматов и передаёт результат в `effectiveSupport.webrtc` (иначе WebRTC отключается и выбирается следующий формат). Сейчас проверка происходит один раз; нужно, чтобы результат обновлялся со временем, и если WebRTC пропал/появился — при необходимости пересмотреть выбранный формат.

**Внимание.** Не сломать существующую логику выбора формата: `selectBestFormat()` в `src/utils/streamFormats.js`, приоритет `webrtc > hls > fmp4`, список `triedFormats`, `handleError` fallback. Изменение доступности WebRTC не должно дёргать плеер каждые 5 секунд — только фактическая смена состояния.

### 3b. Ленивая загрузка hls.js

**Где.** `src/components/cams/HLSPlayer.jsx` — единственное место в проекте, импортирующее `hls.js` (статический `import Hls from 'hls.js'` в шапке файла). Внутри используется `Hls.isSupported()` и создаётся инстанс.

**Что сделать.** Заменить статический импорт на динамический `await import('hls.js')` внутри того места, где реально стартует HLS-воспроизведение (не в начале модуля и не на этапе рендера). Тогда те, кто смотрит WebRTC/fMP4, вообще не грузят 500 kB.

**Важно.** Учесть, что там есть нативный путь HLS (`video.canPlayType('application/vnd.apple.mpegurl')` — используется в `src/utils/streamFormats.js`), для которого hls.js не нужен; не грузить библиотеку, если пойдёт нативный путь. Состояния загрузки/ошибок должны остаться корректными (`status`, `errorMessage`, `onError`, `onPlaying`).

## Задача 4. Убрать вкладку «Снимок» из редактирования камеры (НЕ СДЕЛАНО, явно запрошено)

**Где.** `src/pages/CamDetailPage.jsx` — в массиве `TABS` есть запись `{ key: 'snapshot', label: 'Снимок' }`, и где-то ниже рендерится `{activeTab === 'snapshot' && <CameraSnapshot ... />}`.

**Что сделать.** Удалить и запись из `TABS`, и соответствующий блок рендера.

**Контекст.** Снимок теперь показывается превью на карточках камер в главном меню (`src/components/cams/CamCard.jsx` — тянет `/cams/{id}/snapshot` через `fetch` с `Authorization: Bearer <accessToken>` и показывает `URL.createObjectURL(blob)`; пока снимка нет — чёрный прямоугольник с текстом «Нет снимка»). Компонент `src/components/cams/CameraSnapshot.jsx` после этого останется неиспользуемым — проверить, не импортируется ли он ещё где-то, и если нет, можно удалить файл.

**Не забыть.** После удаления вкладки проверить, что индекс активной вкладки/дефолтный `activeTab` не сломался (массив вкладок меняет длину).
